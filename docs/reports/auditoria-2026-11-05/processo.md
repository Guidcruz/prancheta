Base: `git log origin/main fb313d0..5498ccc`, metadados e corpos dos PRs #16–#31 (REST), 60 execuções do CI, ruleset `proteger-main`, `/home/user/prancheta/CLAUDE.md`, `/home/user/prancheta/docs/PROCESSO.md`, `/home/user/prancheta/docs/papeis.md`, `/home/user/prancheta/docs/DEFINITION-OF-DONE.md`, `/home/user/prancheta/.claude/settings.json`, `/home/user/prancheta/.claude/hooks/guard-git.sh`, `.claude/agents/*`, `.claude/skills/*`. Não há arquivo de memória do Claude Code para este projeto (`~/.claude/projects/-home-user-prancheta/` só tem a sessão); nada a conferir nesse ponto.

**O que foi conferido e está em ordem:** todos os 16 PRs foram mergeados por squash pela conta do CEO, nenhum commit entrou na `main` fora de PR; a ruleset exige PR, CI `ci` verde e só squash; as travas (`settings.json` + hook) cobrem `gh pr merge`, `gh api .../merge`, push na main, tag, `reset --hard`, apagar branch, rebase; os 21 commits `fix:` dentro dos PRs vêm com teste (exceções triviais: `bb8c2cd` só `package.json`, `2119ab0`/`8939d58` só texto do site); o CHANGELOG "Não lançado" foi atualizado em todos os PRs de código; devlog em dia (Dia 1 em 03/11, Semana 1 em 05/11); as decisões do CEO por tarefa estão registradas em `docs/status.md` e nos docs de design, e os ADRs 0015–0017 saíram no mesmo dia da decisão.

## Achados

### Crítico

**1. Todos os PRs saem da mesma branch de sessão, e o PR aberto recebe commits depois do veredito dos portões.**

- Evidência: `head: claude/kickoff-i22gas` nos 16 PRs (#16–#31; também #2–#15). O checklist "Branch `feat/`…" está desmarcado nos 16 corpos, com a nota "branch de sessão, definida pelo ambiente". Após cada squash a branch volta a ser idêntica à `main` (`git log` linear, `5498ccc` nas duas), ou seja, é recriada/ressincronizada a cada merge. Corpo do PR #27: "Esse commit chegou segundos depois do merge do PR #26 e ficou de fora". PR #22: `b19b9f7` (fix de CI) e `ba6d59e` (`CLAUDE.md`) entraram às 21:47 depois do QA, com o PR já aberto. PR #29: `bcfd6c2`, `e108b1e`, `8b3b14d`, `b2e3c11`, `64c8b87` (ADR-0016, plano de áudio, 3 mudanças de site) entraram depois do review da T-015. PR #31: ADR-0017 e pesquisa do STJD junto da T-017.
- Impacto: o escopo revisado e testado não é o escopo mergeado; viola `docs/PROCESSO.md` §3 ("nunca pule etapas"), §7 ("PRs de uma história por vez"), `docs/DEFINITION-OF-DONE.md` item 1 e a convenção de branches do `CLAUDE.md`. Gera o retrabalho recorrente de recriar a branch e a corrida de commits perdidos.
- Recomendação: uma branch por tarefa (`feat/t-0NN-slug`), criada a partir de `origin/main`; o Orquestrador confere `git branch --show-current` antes de delegar (PROCESSO §7 já pede). Se o ambiente obrigar a branch de sessão, então: oficializar no `CLAUDE.md`/DoD/template e proibir qualquer commit na branch enquanto houver PR aberto dela (o hook pode bloquear `git commit` quando `gh pr view --json state` devolver OPEN para a branch).

### Alto

**2. Os vereditos dos portões só existem no texto do PR escrito pelo próprio Orquestrador; autor, revisor e quem faz merge são a mesma conta.**

- Evidência: zero reviews no GitHub nos 16 PRs (`/pulls/N/reviews` vazio); ruleset com `required_approving_review_count: 0`; `user` e `merged_by` = `Guidcruz` em todos; o comentário do PR #22 está assinado por `Guidcruz` com rodapé "Generated by Claude Code". Não há `docs/reviews/`, `docs/bugs/` nem relatório salvo em `docs/reports/` (só o template). O "BUG-A" do PR #31 só aparece em `docs/design/temporada.md:195`.
- Impacto: "merge só pelo CEO" e "ok do CEO antes de cada item" são inverificáveis pelo histórico; um veredito APROVADO/PASS não pode ser auditado nem reproduzido.
- Recomendação: guardar o relatório do `code-reviewer` e do `qa-engineer` (veredito, totais, lista de apontamentos) no PR como comentário ou em `docs/reviews/PR-NNN.md`; o CEO aprova o PR no GitHub ("Approve") como registro do seu ok e sobe `required_approving_review_count` para 1.

**3. PRs com mais de uma história e tamanho G sem aprovação explícita.**

- Evidência: #16 (`feat(site)`) traz site novo, gerador de escudos, campos `crest*` em `ClubDef`, `ENGINE_VERSION` 3, ADR-0014 e revisão do ADR-0013: 28 commits, 88 arquivos, +5.347. #28: 29 commits, 65 arquivos, +6.126 (T-016 + texto de instalação do site + ideias no status). #29: T-015 + ADR-0016 + 3 commits de site. #31: 29 commits (T-017 + ADR-0017). #26: +34.503 linhas (goldens).
- Impacto: um PR `feat(site)` mudou o motor e o formato do estado; revisão de 29 commits em uma rodada dilui o portão; a DoR (`docs/DEFINITION-OF-DONE.md:8`) pede "P ou M; G é dividida ou aprovada explicitamente".
- Recomendação: um PR por tarefa; ADR, pesquisa e textos de site em PR `docs/` ou `quick/` próprios; marcar tamanho (P/M/G) no corpo do PR e registrar o "G aprovado pelo CEO".

**4. O portão "CEO testou e fez o merge" dura minutos em PRs de milhares de linhas.**

- Evidência (criado → merge): #24 00:12→00:15 (+4.562), #25 01:23→01:27 (+4.249), #28 13:03→13:07 (+6.126), #31 18:42→18:46 (+4.142), #26 02:42→02:49 (+34.503), #22 21:44→21:49.
- Impacto: o item 23 da DoD é formal, não real, para PRs só de motor (sem tela). O processo diz uma coisa e pratica outra.
- Recomendação: o CEO decide o que o portão significa para PR de motor: (a) ler a tabela de métricas/golden e os riscos listados pelo QA, com "passos de teste manual: N/A (só motor)" explícito; ou (b) aceitar por escrito que o portão é só o merge. Para PR com tela, o teste manual continua obrigatório.

**5. `main` ficou vermelha duas vezes e a correção levou 9 PRs.**

- Evidência: runs de push na `main` em 2026-11-04 01:52 (#2) e 13:29 (#13) falharam em `astro check` ("Node.js v22.23.3 is not supported by Astro") enquanto o PR correspondente passou (runner sorteava outra 22.x). Correção só em `b19b9f7` (PR #22, 21:47), embutida numa tarefa de motor; sem nota em `docs/status.md` nem no CHANGELOG; L3 (fixar ações por SHA) segue aberto em `docs/status.md:271`.
- Impacto: "regressão verde na `main`" (Release Done) não valeu por ~20 h; a causa (versão flutuante) é a mesma do L3.
- Recomendação: regra escrita: `main` vermelha é prioridade zero, PR `fix(ci)` próprio pelo `devops-engineer`, registrado no status; fechar L3.

### Médio

**6. Linha de assunto dos commits na `main` em português em 7 dos 16 squashes.**

- Evidência: `5498ccc`, `6163bcd`, `752aaa7`, `fad4923`, `4e6a4b5`, `82cd98c`, `56fddbc` (títulos de PR em pt-BR; repo com `squash_merge_commit_title: COMMIT_OR_PR_TITLE`). `CLAUDE.md` "Convenções": commits em inglês; tabela de idioma: "linha de assunto dos commits: inglês", mas "PRs: português". A regra é contraditória com a configuração do squash.
- Recomendação: decidir: título do PR em inglês (Conventional Commits) com corpo em português, ou aceitar assunto em pt-BR e corrigir o `CLAUDE.md`. O template do PR deve dizer qual.

**7. Retrabalho recorrente de formatação (Prettier) e de CHANGELOG.**

- Evidência: CI do PR #26 falhou em `prettier --check` (`docs/03-test-plan.md`); commits só de formato: `7c6e2a7` (#18), `4882273` (#21), `be8c694` (#22), `240ae40` (#16), `d8d68e2` (#26), `12ed038` (#26); `7bc95f1` (#29) "merge duplicated Unreleased sections" no CHANGELOG.
- Impacto: tempo e commits de ruído; a tabela do plano de testes tem células de centenas de caracteres que o Prettier realinha a cada edição.
- Recomendação: `npm run format` no procedimento do `developer`, `qa-engineer` e `tech-writer` antes de commitar (ou um hook `pre-commit` com `prettier --write` nos arquivos staged); converter a tabela de `docs/03-test-plan.md` em lista ou colocá-la no `.prettierignore`.

**8. PR do devlog quebrou o teste de conformidade do patrocínio porque o caminho leve não roda `npm test`.**

- Evidência: run de 2026-11-05 02:59 (#27) falhou em `src/lib/sponsorship.test.ts`; 2 commits de correção (`64263a7`, `17cbe49` "Brasileirão"); corpo do PR #27: "QA N/A: build do site ok; content:check ok; Prettier ok". `.claude/skills/devlog/SKILL.md` passo 2 manda só `npm run build -w site`; `.claude/skills/quick/SKILL.md` passo 4 diz "lint e testes verdes" sem nomear o comando.
- Recomendação: `/quick` e `/devlog` exigem `npm run test:all` antes do PR (o teste do site varre `dist/`, por isso o build precisa vir antes).

**9. `docs/decisions.md` parou no ADR-0015.**

- Evidência: tabela termina em 0015; `docs/adr/0016-audio-essencial-sem-custo.md` e `0017-efeito-suspensivo-fiel-ao-real.md` estão "Aceito (CEO, 2026-11-05)".
- Recomendação: `tech-writer` adiciona as duas linhas; o passo "ADR novo" do `/feature` inclui "atualizar `docs/decisions.md`".

**10. `docs/status.md` e `CLAUDE.md` dizem "em andamento/PR aberto" para o que já foi mergeado.**

- Evidência: `docs/status.md:76-79` ("PR aberto" para T-014, T-015, T-016, T-017), `:332-335` ("Em andamento: T-014, T-016: PR aberto"); `:3` promete "atualizado a cada merge"; `CLAUDE.md:15` "T-001 a T-003 feitas". Causa estrutural: o status é escrito dentro do PR, antes do merge, então sempre nasce desatualizado.
- Recomendação: escrever "PR #N" sem estado; `CLAUDE.md` só aponta para `docs/status.md`; e um passo pós-merge no `/feature` (uma linha, caminho leve) ou aceitar que o status descreve "até este PR".

**11. `docs/papeis.md` aponta os parâmetros para dentro do motor.**

- Evidência: `docs/papeis.md:12` "`app/src/engine/params/`"; `CLAUDE.md` e o lint de fronteira dizem `app/src/params/` (o motor não pode importar `params`).
- Recomendação: corrigir para `app/src/params/`.
